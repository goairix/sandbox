# Next target integration — read-only candidate notes, not a formal interface

Current formal confinement/drain tasks and their independent gates come first. This note does not create another passive delivery claim or approval handoff. Next implementation should combine actual protected target activation, acceptance and monitor execution rather than extend diagnostic-only state again.

## Current seams inspected
Overall approved design physical sections180..275: close permanent etcd admission then persistent target gate before BOTH operation-prefix and accepted-target drain; process exit does not settle remote writes. Target exact UID+fresh per-container boot is mandatory; image quota overhead and protected FD/capability policy are required. Current controltarget Journal is closed-only diagnostic state, record state unknown; no accepted/open/terminal/GC. Current pure ExecStartEvidence explicitly does not prove issuer-active/liveLease/committed intent/open gate. Backend PreparedExecEffect holds private original backend/cap/draft, Reference is diagnostic; its sign is before Stage, so ticket alone is not delivery commit proof.

## Concrete integration risks to formalize
A target cannot derive independent expected dynamic operation context merely by copying an untrusted ticket. Trusted sender assertion plus target-independent activated static identity is needed. Original Prepared transport must revalidate original capability/26 metadata fences/time immediately before each delivery; no public payload/ticket/raw-start shortcut or historical resume. Start acceptance acknowledgement must return before waiting for completion to avoid holding original cap.mu and preventing Renew. Metadata cancellation/Lease expiry cannot be a process End.

A protected Unix socket/root-only fixed bridge plus authenticated backend delivery may be a transport candidate; root-peer SO_PEERCRED alone does not prove metadata commitment. Existing certificate purposes delegate identity, not physical effect authority. Need precise root/issuer activation, request-purpose separation, trusted operator custody and clocks rather than claiming the existing ticket proves all prerequisites. Preserve mTLS boundary in the approved overall architecture; fixed Docker/Kubernetes exec may only enter an immutable trusted bridge with non-user argv and framed stdin. User program never runs in the bridge/sidecar, and raw exec/file/stream bypasses must be removed when wired.

Fresh BootID must be generated by each launcher start; host /proc/sys/kernel/random/boot_id is not a per-container restart identity. PodUID staying equal across container restart cannot preserve the old activation. Bootstrap/actual runtime identity certification must be source-specific and verified against Docker/Kubernetes actual exact object identity, not a copied configuration claim. Root trust/current issuer updates remain closed until complete; missing state never auto-adopts old capability.

Native tests' test-only spawn already prove credential/FD behavior but are not production launch wiring. Monitor constructor/drain is cleanup-only. Actual target should durably accept before its one serialized spawn, close all management FDs, set exact signed UID/GID/complete env/cwd/argv/stdin/TTY, and report completion only after local all-descendant drain. Monitor loss must keep unknown and perform later PID1 namespace-wide cleanup. Sole wait owner may consume statuses for adopted children; future command result must identify the actual expected root and handle missing root status conservatively, not derive ExitCode from an arbitrary reap.

FUSE currently needs its own trusted privileged mounter. User launcher bootstrap expects exact initial four caps; an initial SYS_ADMIN FUSE topology cannot silently bypass that check. Decide and test actual mounter-before-drop or separate-container topology with existing original workspace/mount/network/cgroup identity, target incarnation, protected credentials and quotas. No extra SYS_ADMIN in the user launcher contract. A new image must contain trusted immutable launcher/bridge and replace sleep PID1; tag alone is not a trusted immutable fingerprint.

Clock contract still needs operator-authenticated source/error/age, neutral shared abstraction and no time.Now fallback for capability safety. Local drain's monotonic deadline is not that authenticated UTC clock. Common observation adapters must avoid per-idle target etcd clients/leases or per-sandbox RPC heartbeat.

## Capacity and honest performance boundary
Confinement and local drain only work on startup/active commands; an extra monitor is active-C overhead, not idle-N control polling. Actual Go runtime/PID1 fixed RSS/threads/filter storage/startup is still a fleet cost. Existing test binary RSS~9.5MiB is not production overhead; measure actual minimal production launcher and original image at same quota, both startup and active peak. Shared mapped code may make sum-RSS differ from node memory/cgroup charges, so do not multiply test RSS by N and call it a measurement. Exact original quotas/minimum viable memory+pids must be reported, not expanded silently.

High idle-N control-plane gains still require shared watches/bounded due windows/worker claims/collector/GC and final production Redis removal. Current new code does not change actual production Manager or claim improved end-to-end p99. Metadata at10k/100k/1M and runtime counts are separate physical benchmarks with resource-permitted bounds.

## Candidate actual target unit, still not formal or approved interface
Combine protected activation, accepted/terminal journal transitions, actual PID1/monitor execution and opaque Prepared delivery in one next unit, followed by transport/image wiring gates. Do not add another closed-only diagnostics deliverable. A possible fixed Docker/Kubernetes exec entry is an immutable root-only byte relay to the launcher Unix socket, with mutual TLS running end-to-end between API's private management key and launcher (the relay must never receive a serialized API private key). Existing management certificates are custom signed identity records, not automatically X509 or execution grants; any TLS representation must explicitly bind handshake key possession to pinned root, purpose, exact current issuer/runtime identity and validity. This is an unresolved design requirement, not a finished authentication claim.

Prepared delivery must remain inside original Backend/capability origin: current exact metadata fences and original deadline are checked after any handshake delay immediately before payload delivery. An authenticated sender assertion may supply trusted dynamic operation expectations while the target independently uses protected activated static target identity; copying an untrusted ticket into expected context is prohibited. The target still validates signed complete request/ticket and current activated epoch/issuer, then durably accepts before its exactly one serialized user spawn. Initial acknowledgement must precede long completion waiting so cap.mu does not block renewal. Historical record loading and public getters remain diagnostic, not delivery reconstruction.

Actual monitor orchestration must preserve original command/env/cwd/stdin/TTY semantics, one root PID identity/status, no concurrent Wait4/Cmd.Wait and no new trusted spawn during drain. os/exec startup-error internal wait behavior and root PID reuse/result attribution need explicit treatment. Active command count adds monitor processes/threads within original cgroup quotas; measure minimal production launcher and active peaks, and make spawn resource failures conservative without silently increasing memory/pids or interpreting cancellation as completion. Idle launcher runtime overhead remains N-proportional physical cost even when its state control plane has no idle per-sandbox lease/timer.

## Narrow TLS transport research (candidate, not a production grant)
Primary Go docs https://pkg.go.dev/crypto/tls and current Go1.25.6 src/crypto/tls/common.go625..654/684..690/713..730 were checked. VerifyPeerCertificate does not run on resumed sessions; VerifyConnection runs on every connection. A future custom signed-identity/pinned-key bridge must use real mandatory bidirectional TLS key possession with a complete fail-closed verification callback, never naked InsecureSkipVerify. Disable session tickets/cache for initial implementation, and still recheck active issuer/boot/gate/time per request rather than treating a completed handshake as an execution grant.
Existing command/runtime identity certificates are custom Ed25519 records, so they cannot be passed directly as X509 TLS chains. Candidate: narrowly constrained TLS leaf plus an exact independently trusted identity-record/key binding; this remains to be formalized and tested against mismatched peer key/role/root/boot/expiry/issuer, not a selected policy yet. Current ExecCommandIssuer only signs fixed start claims; TLS key custody/signature support cannot be invented by extracting a key from it. Concrete transport/provider ownership and protected runtime bootstrap signing still need design before next implementation.
Current AuthorityClock abstraction is in etcd/publication_authority.go and requires controlled call-time UTC/verified uncertainty, context honoring and immutable concurrency safety. The backend adds measured elapsed time and rejects uncertainty+elapsed over1s. A target needs an independently trustworthy fresh observation; copying sender UTC or using local time.Now with zero assumed error does not meet that contract. A neutral adapter and concrete operator time source are next-unit dependencies, not new per-idle target etcd clients.

## User execution compatibility risks to pin in the combined target unit
Current ExecRequest.LineBuffered allocates a real TTY in both Docker and Kubernetes; it is not just a stream buffer flag. New protected monitor execution must preserve real PTY semantics/controlling terminal and merged stderr, not silently implement pipes when signed TTY=true. Existing x/sys/unix and moby/term/xterm dependencies are present, but no new PTY dependency or implementation choice selected yet. Native pty ownership/session, original quota, cancellation and reader joins need explicit tests.
Original default image environment/PATH plus caller env, exact cwd and argument lookup are another compatibility seam. Go exec.Command resolves a bare executable using the parent's current PATH before cmd.Env applies; the target must deliberately resolve the user's effective PATH rather than management environment. Management mode/config env must never be overwritten by user Env. Credential groups must be explicitly cleared, all management FDs CLOEXEC/closed, stdout/stderr only user-selected streams, and ExecStart ACK must return before its long wait. Pdeathsig for direct root, if used, cannot by itself prove all descendants terminate on monitor loss; later closed-gate PID1 escalation remains necessary.

Target activation must independently pin the original sandbox user UID/GID and immutable image/security/topology contract. A correctly signed descriptor containing an arbitrary other nonzero UID is not enough to change the sandbox execution identity; target admission must require those activated values. Concurrent commands intentionally share a sandbox/user namespace, so the two-monitor drain proof establishes management drainer attribution, not a new promise that same-UID user programs cannot signal each other. PID1 escalation must stop/join registered management owners before becoming the sole user reaper, keep the target gate closed and distinguish local no-writer observation from remote-write settlement.
