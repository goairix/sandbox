# Authenticated target execution implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver original etcd exec capabilities to an independently activated authenticated PID1, durably accept and execute exact user commands, renew accepted commands and report honest local terminal/unknown outcomes.

**Architecture:** Protected Unix byte relay with end-to-end pinned mutual TLS; fresh root-certified birth and gate; original backend fencing followed by one-use accepted monitor registration and actual descendant drain. All four tasks form one physical unit; the final gate requires actual user execution, not just new diagnostic records.

**Tech Stack:** Go1.25 CGO0, standard crypto/tls/x509/Ed25519, existing x/sys/unix, existing etcd3.6 client, root-owned bounded files, already-local controller-owned native fixture.

**Spec:** `docs/superpowers/specs/2026-10-07-authenticated-target-execution-design.md`

## Review Focus

1. Delayed handshake or fresh wrong birth/issuer can invalidate previously prepared authority; Task1 authenticates peers and Task4 repeats original fences/time before payload.
2. Persistence after accepted or monitor startup can be uncertain; Task2 retains unknown/no replay and Task3 isolates rather than forging a terminal result.
3. User PATH/env/TTY/stdio can differ from management process defaults; Task3 actual user/PTY/FD tests pin signed values and no management mode/key inheritance.
4. Root exit alone misses adopted live descendants and missing-root status can misattribute exit0; Task3 exact root/sole wait/native descendant tests pin attribution and full drain.
5. A lost API connection or accepted renewal race must not remint/replay/extend terminal work; Task2 renew/terminal persistence and Task4 original-handle/delayed/cancel/dedup tests pin this.
