# 普通池竞争、工作区销毁指标和上传验收整改方案

## 范围与基线

用户同意优先处理普通池竞争、sync/FUSE 销毁指标去重和上传成功响应校验。本文是待确认的小范围实现规格，不是代码已经修复或线上已经部署的声明。

代码基线为 `adf8f69`，当前分支 `feat/workspace-fuse-mount`，直接在当前工作区处理，不创建 worktree。用户统一构建、推送镜像和升级部署；本次不改线上 release、节点、Pod、Redis 数据或网络策略。

最新 [v0.3.25 验收](../../testing/2026-09-14-v0.3.25-concurrent-destroy-validation.md) 已验证普通并发销毁 24/24 成功、综合 API 与有界 FUSE 文件压力通过、普通/FUSE 池各 3 个 prepared。以下工作不重开已经关闭的普通并发 503，也不修改现有 API、values 或 Redis 持久化结构。

本轮不处理普通销毁约 30 秒的性能、FUSE 创建长尾、全仓历史 lint 告警、Redis/CNI 故障注入或其它网络插件现场验收。

## 实现方式比较

1. **推荐：在原有状态机内区分合法竞争和实际完成者。** 后台扫描检测到快照变化后有界重读并重新判定；工作区清理向调用层返回实际完成结果；上传助手校验完整响应。取池仍使用现有 CAS，无新增全局热点锁或指标 Redis 写入。
2. **扩大共享锁范围，串行取池与扫描。** 竞争更易理解，但慢 Kubernetes/存储调用可能阻塞多副本取池，影响性能和可用性，不采用。

## 一、普通池状态竞争

### 证据和问题

线上并行测试出现两条 `clean unhealthy ordinary runtime: ordinary pool record changed before cleanup claim`。源码中扫描先读取 prepared 记录，`recordedInventory` 再读取 Pod 业务标签视图；若期间被领取、迁移或确认消费，旧 prepared 快照可能进入 unhealthy 路径。`cleanupRecord` 的 CAS 会拒绝旧状态清理，保护了运行时，却将该次合法竞争作为错误中止 refill。

该代码窗口与日志吻合，但日志缺少 runtime ID，尚不能逐条还原现场实例。实施前必须通过可控交错的回归确定性复现，而不是假定所有 CAS 失败都属合法领取。

### 设计约束

- 只在后台扫描的状态判定路径处理合法快照竞争，不把取池加进后台共享锁。
- 清理认领 CAS 不匹配时，读取并校验最新记录，按最新状态重新判定；合法 claimed 或记录已消失不继续删除旧 runtime。
- 有界刷新扫描状态，保证孤儿处理和容量判断不再使用失效快照。不能只让 `cleanupRecord` 返回 nil、然后按已清理删除本地索引并继续旧孤儿扫描。
- 最新记录仍为 preparing/prepared/cleanup 时按其现有状态、revision 和精确 runtime UID 重新判断，不把其它状态一概解释为领取成功。
- 持续竞争的重试必须有次数和 context 边界；不增加无限重读或全业务库存扫描。
- 存储错误、损坏记录、非法状态、UID 变化和真实终止未确认仍失败并保留恢复证据；不通过降低错误等级掩盖它们。
- 只有成功持有清理状态的实例执行精确运行时删除及策略收尾，保留同名 replacement 防护。
- 稳态 refill 保持按当前池记录检查库存；只有原本允许的启动/孤儿恢复路径广扫。

### 验收

确定性覆盖 prepared 快照后被 claimed、消费确认导致记录消失、Pod 业务身份迁移与扫描交错；健康业务 runtime 不误删、不重复发布、不作为孤儿重新收录，后续容量可恢复。分别覆盖启动扫描和稳态 refill，并保留真实存储错误、坏状态、同名新 UID、未确认终止和缺失 Pod 后策略收尾负例。内存与独立真实 Redis 上验证需要依赖原子操作的交错，运行 race 和重复轮次。

## 二、sync/FUSE 并发销毁指标去重

### 证据和问题

普通分支已经返回实际完成标记，让等待者不重复扣减 `sandbox.active`、累加 `sandbox.destroy.total`。工作区分支仍无条件返回 `true` 加清理错误；多个等待者都成功时，调用层仍可能重复计数。参考 [普通整改说明](../../testing/2026-09-14-ordinary-concurrent-destroy-remediation.md)。

### 设计约束

- 将工作区内部完成结果区分为实际完成收尾和等待/观察历史完成，传播给既有指标调用层。
- 只有实际完成者记录该次请求的销毁指标；同副本多个等待者、跨副本等待者和历史完成确认者不再重复计数。
- 覆盖 FUSE、sync、sync final-output checkpoint 恢复及 interrupted transition，不能仅修一个正常路径。
- 保留现有 fenced controller、生命周期互斥、最终输出 checkpoint、精确 runtime UID 和持久化缺失确认；错误、取消、超时不伪造完成。
- 不新增每次 DELETE 的指标专用 Redis key、分布式锁或永久本地 ID 去重集合，不将指标修正变成业务清理的新依赖。
- 保持现有 manual/到期/恢复路径的语义，不借本轮重构全部遥测。指标仍是 best-effort 观测，不承诺跨进程崩溃事务级 exactly-once，也不把每个副本的增减量指标宣称为独立 release 总量。

### 验收

在 SDK ManualReader 中创建一个沙盒并并发销毁，正常完成后的聚合 active 为 0、destroy.total 为 1。覆盖 ephemeral/persistent、sync/FUSE、同副本和跨副本、checkpoint 恢复；实际 runtime 只删除一次，session/owner/lease/active 完整收尾。等待者取消、持久化未确认、同名 replacement 和失效 owner 接管仍符合既有失败/恢复语义；内存与独立真实 Redis 相关路径均验证。

## 三、大文件上传助手成功响应校验

### 证据和问题

`test/integration/workspacefuse` 的 `uploadSized` 目前仅检查 HTTP 2xx，不读取成功 JSON。历史上传后文件缺失的失败在换网后未复现，精确原因未完全确认；不能把这次测试加强说成已经修复某个已确认的服务端上传缺陷。

现有服务端直接上传成功为 HTTP 200、`FileUploadResponse{path,size}`，无需新增接口字段。

### 设计约束

- 要求 HTTP 200，有限长度读取完整响应，严格验证 JSON 只包含一个完整值、`path` 和 `size` 必须存在并匹配请求。
- 空 200、204、损坏/截断/超限 JSON、尾随额外内容、错误路径或大小、响应读取失败均视为上传失败。
- 正确关闭响应体和 pipe；HTTP 提前返回、请求失败或 context 取消时上传 producer 必须能退出，不遗留 goroutine，不按文件尺寸申请整块内存。
- 错误日志有界且脱敏，不打印 API key 或存储凭据。
- 保留现有实际文件大小、FUSE 文件语义、flush 和销毁检查；不以响应字段替代后端实际验证，不扩大本轮上传规模。

### 验收

使用本地 httptest 服务验证合法响应、缺失字段、零大小合法响应、错误 path/size、空响应、截断、尾随值、超限响应、非 200、网络/读取错误、取消和提前响应等边界。合法流式请求的实际字节数保持正确，早退 producer 能退出。用户更新镜像后再显式运行有界线上 FUSE 上传专项；本地助手测试通过不算线上结果。

## 实施顺序与交付

1. 用户确认本文；制定实施计划。
2. 三项分别先补回归，观察旧实现按预期失败，再修改对应最小生产/测试代码。
3. 运行目标测试、重复 race、相关包 vet、相对本轮基线的增量 lint，以及全仓 Go 回归；真实 Redis 仅用独立本地临时实例，不指向线上状态库。
4. 自审安全分支、后台扫描不阻塞、producer 退出及指标实际完成者边界。默认跳过的真实部署/故障用例不写成通过。
5. 记录中文整改报告并提交代码；构建和线上升级继续由用户执行，不自动部署。

预计部署无需新增 values 配置，产品修复涉及 API 镜像；是否需其它镜像重建以最终实际变更为准，不能在实施前把镜像发布或线上通过写成既成事实。
