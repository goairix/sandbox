# Helm Chart 0.3.0 与 Sentinel 升级整洁性设计

## 背景

内置 Redis Sentinel 已把启动、身份核验和初始化职责拆到独立的
`sandbox-redis-bootstrap` 镜像，并保证只更新 API 镜像时 Redis StatefulSet
模板不会变化。但当前 Chart 仍有三个发布与验收缺口：

1. Chart 元数据仍是 `0.2.0`，无法明确识别本轮独立 Helm 发布。
2. 每个 Helm revision 都创建新的 identity 和 initialize Job；即使 Sentinel 已经
   初始化完成，与 Redis 无关的升级也会产生两个 Completed Pod。
3. “只更新 API 不重启 Redis”和 FUSE refill lease 45 秒接管边界缺少可重复、
   失败即停止的线上验收工具。

本设计只处理上述发布、Job 生命周期和验收能力。普通沙盒销毁耗时及 FUSE 创建
长尾属于后续独立性能任务，不在本次范围内。

## 版本边界

本轮仅把 `deploy/helm/sandbox/Chart.yaml` 的 `version` 从 `0.2.0` 调整为
`0.3.0`。`appVersion` 和全部镜像 tag 保持现状。

这样 Helm release 能识别本轮 Chart 版本，同时不会暗示 API、AppArmor Loader、
Redis 或 Redis Bootstrap 镜像已经完成 `v0.3.0` 的统一构建。统一清空并重新构建
镜像时，再单独更新 `appVersion` 和 values 中的镜像 tag。

部署文档必须在升级前验证：

- `helm show chart` 输出的 Chart `version` 是 `0.3.0`；
- `helm lint` 通过；
- 使用线上 values 的 server-side dry-run 通过。

## Sentinel Job 条件渲染

### 状态来源

`sandbox.sentinelState` 继续以 Kubernetes 实时对象为唯一判定来源，不增加可由
values 伪造的开关。helper 在原有 `data`、`clusterID`、`freshClusterID` 和 PVC
annotations 之外，返回：

- `identityExists`：目标身份 Secret 是否真实存在；
- `phase`：`cluster.json` 中的 `Pending` 或 `Initialized`。

保留状态必须具有合法 phase。缺失或未知 phase 视为状态损坏并停止渲染，不能把
损坏状态误判成一次新安装。

### Identity Job

只有身份 Secret 不存在时，才渲染 identity Job 及其 ServiceAccount、Role、
RoleBinding：

- 全新安装使用自动身份时，Job 创建不可变身份 Secret；
- 全新安装指定外部身份 Secret 但 Secret 不存在时，Job 给出明确失败，不静默生成；
- 已保留 state/PVC 但身份 Secret 缺失时，helper 仍在模板阶段 fail closed，不允许
  identity Job 为旧数据生成新身份；
- 身份 Secret 已存在时，普通升级不重复核验 Job。Redis Pod 内的身份辅助容器以及
  API startup probe 仍持续执行运行时身份和拓扑校验。

### Initialize Job

只有有效状态 phase 为 `Pending` 时，才渲染 initialize Job 及其
ServiceAccount、Role、RoleBinding：

- 全新安装和中断后重试会继续渲染，并把状态推进到 `Initialized`；
- `Initialized` 的健康 release 在无关升级中不再创建初始化 Job；
- 初始化 Job 仍是普通 Helm 资源，不改成 hook，避免它与 StatefulSet/API 等待关系
  形成启动死锁。

Job 继续使用带 release revision 的名称。第一次从旧 Chart 升级到本设计时，若
集群状态已是 `Initialized` 且身份 Secret 存在，新 manifest 会省略两个 Job 及其
RBAC。Helm 只会处理当前 release manifest 仍在跟踪的旧资源；更早 revision 已经遗留
成孤儿的 Completed Job/Pod 不保证由后续 upgrade 回收，继续依赖原 Job 的 24 小时
TTL。后续普通升级不再生成新的 Completed Pod。

### 失败与恢复边界

- 实时 `lookup` 不可用或返回状态损坏时，不猜测、不重建身份，升级失败。
- `helm template`/`helm lint` 没有集群实时对象，因此按全新安装渲染两个 Job；这既
  能覆盖安装清单，也不会冒充线上升级判断。
- 安装中断且状态仍为 `Pending` 时，下次 upgrade 使用新 revision Job 名重新执行；
  旧 Job 不能因不可变字段阻止恢复。
- Job 成功后的持续安全保证由三副本 Redis/Sentinel readiness、身份辅助容器和 API
  startup probe 承担，不依赖保留 Completed Job。

## API-only 升级验收

新增只读的升级快照与比较脚本。脚本分为 `snapshot` 和 `verify` 两个显式阶段，
不替用户执行 `helm upgrade`，也不读取或输出 Secret 内容。

快照记录：

- kube context、namespace 和 release；
- API Deployment 当前镜像和 rollout 身份；
- Redis StatefulSet `currentRevision`、`updateRevision` 和 PodTemplate 摘要；
- 三个 Redis Pod 的名称、UID、restart count 和 imageID；
- Sentinel identity/initialize Job 集合。

校验阶段要求：

1. context、namespace、release 与快照一致；
2. API Deployment rollout 完成且 API 镜像发生预期变化；
3. Redis StatefulSet revision、PodTemplate 摘要、三个 Pod UID、restart count 和
   imageID 全部不变；
4. Redis/Sentinel 三副本全部 Ready；
5. 已初始化 release 没有新增 identity/initialize Job。

任一条件不满足立即返回非零退出码，并打印具体差异。快照文件只包含资源元数据，
可以保存为本地验收证据。

迁移顺序是：先升级到包含条件 Job 的 Chart，确认没有生成当前 revision 的一次性 Job，
并核对遗留 Completed Job 的 TTL；确认 Sentinel 健康后生成基线快照；再进行严格的
API-tag-only 升级并执行比较。

## FUSE refill lease 45 秒接管验收

增加显式 opt-in 的集成验收，不作为默认单元测试，也不在普通 Helm upgrade 中自动
运行。验收只允许在指定测试 release 上执行，并具有以下 fail-closed 前置条件：

- API 与 Redis/Sentinel 均健康；
- 目标 FUSE 池可唯一识别且有完整预热容量；
- 本次创建的 sandbox、lease token 和观测目标均带唯一测试标识。

测试使用生产 Redis repository 的同一 refill lock 协议，为真实 FUSE pool 获取一把
不续租的 45 秒旧 owner lease，然后通过公开 API 消耗并销毁一个 FUSE sandbox 形成
一个容量缺口。它验证：

1. lease 有效期内其他 API 不会错误补池；
2. 旧 lease 到期后，活跃 API 能在允许误差内取得新 lease 并恢复目标容量；
3. 旧 token 在接管后不能续租或释放新 owner 的锁；
4. 测试 sandbox 被正常销毁，池容量恢复，测试记录无残留。

测试进程异常退出时不手工删除 refill lock；45 秒 TTL 是恢复边界。业务 sandbox、
Redis 身份、Sentinel state、PVC 和非测试 key 均不得删除。若环境不满足前置条件，
测试必须停止而不是修改集群来凑条件。

## 测试策略

Helm 模板测试覆盖：

- 离线全新安装仍渲染 identity 和 initialize Job；
- 模拟身份存在、状态 `Initialized` 的 lookup 响应时不渲染两个 Job及其 RBAC；
- 身份存在、状态 `Pending` 时只渲染 initialize Job；
- 非法或缺失 phase、保留 PVC/state 缺身份时继续 fail closed；
- Chart version 为 `0.3.0`，`appVersion` 和镜像默认值没有随之变化。

升级快照脚本使用静态 fixture 测试成功与每种关键差异的失败路径，再在
`ds-ai-research/aiadp-sandbox-fuse` 上执行一次真实 API-only 升级验收。

FUSE lease 测试先用独立 Redis 验证 token 隔离与 45 秒过期，再在指定测试 release
执行一次受控真实池接管。线上验收结果记录在 `docs/testing/`，但不把凭据、Secret
内容或临时 token 写入仓库。

## 明确不做

- 不修改任何镜像 tag 或 `appVersion`；
- 不合并或比较其它分支；
- 不把 Job 改为 Helm hook；
- 不自动执行 Helm upgrade、删除 Redis/PVC/Secret 或清空业务沙盒；
- 不在本次优化普通沙盒销毁速度或 FUSE 创建耗时。
